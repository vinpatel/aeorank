  <action>
Create `scripts/measure-tests.mjs` (Node ESM, no new dependencies — the repo installs
nothing new this phase). It must:

1. Iterate the explicit 13-package list given in `<interfaces>` above. Do not glob the
   workspace; `packages/config` has a stub test script and would break the run, and
   `packages/wordpress`, `apps/docs`, `apps/marketing` have no suite.
2. For each package run vitest with the JSON reporter into a temp file, e.g.
   `pnpm --filter <name> exec vitest run --reporter=json --outputFile=<tmp>/vt-<pkg>.json`.
   Assume `pnpm build` has already run (turbo's `test` task depends on `build`).
3. Sum `numTotalTests` across reports for `tests`, and sum `testResults.length` across
   reports for `files`. Never count with grep — `it.each` and dynamically generated tests
   are invisible to static counting, which is exactly how the published numbers drifted to
   288 / 637 / 675.
4. Fail loudly (non-zero exit, clear message naming the package) if any report is missing,
   unparseable, or reports failures.
5. Write the same object to BOTH paths:
   `.github/test-count.json` and `apps/marketing/src/data/test-count.json`, shaped as
   `{ "tests": <number>, "files": <number>, "measured": "<YYYY-MM-DD>" }`.
   Two paths, one source: the marketing Astro site cannot cleanly import a JSON file from
   outside its own project root, so CI writes an in-`src` copy for it. Plan 17-06 imports
   `../data/test-count.json` from `apps/marketing/src/components/Files.astro`.

Then run it locally and commit the generated artifacts, so the repo has a valid count
before CI ever runs (the marketing build would otherwise fail on a missing import).

Finally add the consumer markers to `README.md`, immediately after the existing
`<!-- STATS_END -->` line, following the identical pattern:
`<!-- TESTS_START -->` / `<!-- TESTS_END -->` wrapping a shields.io badge of the form
`![tests](https://img.shields.io/badge/tests-<N>%20passing-brightgreen)`.
Populate it now with the measured value; CI keeps it current from here on.
Do NOT hand-edit any other test number in README.md in this plan — the full claim sweep is
plan 17-08 and owns those lines.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Pull request from a fork -> CI runner | Untrusted code executes in the `verify` job |
| CI runner -> `main` (publish-count job) | A workflow writes to the default branch with `contents: write` |
| npm advisory database -> build outcome | External data determines whether the build passes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-07 | Elevation of Privilege | `.github/workflows/ci.yml` | mitigate | Top-level `permissions: contents: read`; `contents: write` scoped to the `publish-count` job, which runs only on `push` to main (never on `pull_request`, so fork PRs cannot obtain write) |
| T-17-08 | Tampering | Dependency tree (transitive) | mitigate | `pnpm audit --audit-level=high` as a dedicated job, required by the ruleset in plan 17-09 — the only gate that reaches pnpm transitives |
| T-17-09 | Repudiation | Published test count | mitigate | Count is emitted by the vitest JSON reporter in a clean CI environment and committed by the bot; hand-edited counts are detectable because they diverge from `.github/test-count.json` |
| T-17-10 | Spoofing | `publish-count` git identity | accept | Commits as `aeorank-bot` using the default `GITHUB_TOKEN`; same trust model as the three existing bot workflows |
| T-17-SC | Tampering | GitHub Actions used | mitigate | Only first-party/widely-used actions (`actions/checkout`, `actions/setup-node`, `pnpm/action-setup`) at major-version tags; no npm packages are installed by this plan |
</threat_model>
