Confirm the gate is green before making it mandatory. Requiring a failing check would brick
the repository:
`gh run list --workflow=ci.yml --limit 1 --json conclusion,databaseId` then
`gh run view <id> --json jobs -q '.jobs[] | {name, conclusion}'`.
Both `verify` and `audit` must read `success`. If `audit` is not green, stop — that means
SEC-01 is not actually closed and plan 17-08 needs revisiting.

Then protect `refs/heads/main` using a **repository ruleset**, not classic branch
protection. Classic protection cannot grant a bypass to GitHub Actions, and D-04 requires
the three bot workflows to keep pushing directly to main without being converted to PRs.

`gh api -X POST repos/vinpatel/aeorank/rulesets` with:
- `target: "branch"`, `enforcement: "active"`
- `conditions.ref_name.include: ["~DEFAULT_BRANCH"]`
- rules: `non_fast_forward`, `deletion`, and `required_status_checks` listing both
  `verify` and `audit` as required contexts with strict-required-status-checks policy
  appropriate to a solo repo
- `bypass_actors`: the GitHub Actions integration (`actor_type: "Integration"`, the
  GitHub Actions app id — resolve it rather than guessing, e.g. via
  `gh api repos/vinpatel/aeorank/installation` or the ruleset UI's suggested actor list)
  with `bypass_mode: "always"`, AND the repository admin role
  (`actor_type: "RepositoryRole"`, admin) so the maintainer can still land an emergency fix.
Do NOT add a `pull_request` rule requiring reviews — this is a solo repository and a
mandatory-review rule with no second reviewer would deadlock it.

Then prove the exemption works rather than assuming it. Dispatch one bot workflow that
pushes to main and confirm it still succeeds:
`gh workflow run readme-social-proof.yml` then poll
`gh run list --workflow=readme-social-proof.yml --limit 1 --json conclusion`.
If it fails on a protected-branch error, the bypass actor is wrong — fix the ruleset, do not
weaken it to `enforcement: "evaluate"` and call it done.

Finally prove the protection is real: attempt a trivial direct push of a throwaway commit
that would fail the checks, confirm it is rejected, and discard it. Record both outcomes.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any contributor (including the maintainer) -> `main` | Previously unprotected with zero required checks; anything could land |
| GitHub Actions bot -> `main` | Four workflows push directly with `contents: write` and must bypass protection |
| npm advisory database -> merge eligibility | An external data source now decides whether a change can land |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-31 | Tampering | Dependency tree over time (recurrence) | mitigate | `pnpm audit --audit-level=high` made a required status check via a repository ruleset — the only mechanism that reaches pnpm transitive dependencies, which were 217 of the 242 baseline alerts |
| T-17-32 | Elevation of Privilege | Ruleset `bypass_actors` | accept | The GitHub Actions integration and the repository admin role can bypass. Required by D-04 so the three existing bot workflows keep pushing; scoped to actors that already hold `contents: write` on this repo |
| T-17-33 | Tampering | `main` history | mitigate | `non_fast_forward` and `deletion` rules block force-push and branch deletion |
| T-17-34 | Repudiation | Claim regression after launch | mitigate | `scripts/check-claims.mjs` runs inside the now-required `verify` job, so a drifted number cannot merge |
| T-17-35 | Denial of Service | Repository becoming unmergeable | mitigate | The `audit` job is confirmed green BEFORE it is made required; the admin bypass actor preserves an emergency path |
| T-17-SC | Tampering | Dependabot-authored PRs | mitigate | Auto-merge deliberately NOT adopted (`allow_auto_merge` stays false), so no dependency update lands without a human looking at it |
</threat_model>
